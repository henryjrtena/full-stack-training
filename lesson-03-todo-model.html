Domain Model

Lesson 3: Creating the Todo Model

The model holds the shape of our Todo data and defines validation rules that both controllers and views can respect.

Introduction

Every MVC application starts with a domain model. For the Todo app, that model needs properties for the task title, details, due date, and completion state.

Key Concepts

  • Models represent application data.
  • Data annotations add validation and UI metadata.
  • Validation errors flow naturally into Razor views.
  • A consistent model makes it easier to switch storage approaches later.

Step-by-Step

Create TodoItem

using System.ComponentModel.DataAnnotations;

namespace TodoMvcApp.Models;

public sealed class TodoItem
{
    public int Id { get; set; }

    [Required]
    [StringLength(120, MinimumLength = 3)]
    public string Title { get; set; } = string.Empty;

    [StringLength(500)]
    public string? Description { get; set; }

    [Display(Name = "Due date")]
    [DataType(DataType.Date)]
    public DateOnly? DueDate { get; set; }

    public bool IsCompleted { get; set; }
}

Why These Attributes Matter

[Required] ensures a title is provided. [StringLength] prevents values that are too short or too long. [Display] improves labels in Razor views, and [DataType] helps render a date-focused input.

Other Common Data Annotations

using System.ComponentModel.DataAnnotations;

public sealed class TodoItem
{
    public int Id { get; set; }

    [Required]
    [StringLength(120, MinimumLength = 3)]
    public string Title { get; set; } = string.Empty;

    [StringLength(500)]
    public string? Description { get; set; }

    [Range(1, 5)]
    public int Priority { get; set; } = 1;

    [Display(Name = "Owner email")]
    [EmailAddress]
    public string? OwnerEmail { get; set; }

    [Display(Name = "Confirm owner email")]
    [Compare(nameof(OwnerEmail), ErrorMessage = "Email addresses must match.")]
    public string? ConfirmOwnerEmail { get; set; }

    [Phone]
    public string? ContactNumber { get; set; }

    [Url]
    public string? ReferenceLink { get; set; }
}

ASP.NET Core supports many validation annotations beyond the basics. [Range] is useful for numbers, [EmailAddress] validates email-shaped input, [Compare] checks that one property matches another, [Phone] helps validate contact numbers, and [Url] is useful when your model accepts links. These attributes work well with both server-side validation and client-side validation in MVC forms.

Formatting and Metadata Annotations

public sealed class TodoItem
{
    [Display(Name = "Due date")]
    [DataType(DataType.Date)]
    public DateOnly? DueDate { get; set; }

    [Display(Name = "Estimated cost")]
    [DisplayFormat(DataFormatString = "{0:C}")]
    public decimal? EstimatedCost { get; set; }

    [ScaffoldColumn(false)]
    public DateTime CreatedUtc { get; set; }
}

Not every annotation is about validation. Some are about display and scaffolding. [DisplayFormat] changes how a value is rendered, while [ScaffoldColumn(false)] can hide fields from generated forms and UI scaffolding.

When to Use Data Annotations Carefully

  • Use them for simple validation rules close to the model.
  • Use them for labels and UI metadata that belong to the model.
  • Avoid putting heavy business rules into attributes when the logic depends on services or database state.
  • For more complex validation, use custom validation attributes, action filters, or service-layer rules.

Bind and Validate in a Controller

using Microsoft.AspNetCore.Mvc;
using TodoMvcApp.Models;

namespace TodoMvcApp.Controllers;

public sealed class TodoController : Controller
{
    [HttpGet]
    public IActionResult Create() => View(new TodoItem());

    [HttpPost]
    [ValidateAntiForgeryToken]
    public IActionResult Create(TodoItem item)
    {
        if (!ModelState.IsValid)
        {
            return View(item);
        }

        return RedirectToAction(nameof(Index));
    }

    public IActionResult Index() => View();
}

Summary

Our TodoItem model is small but complete enough to support validation, forms, and future persistence layers. Next we will render this model with Razor views and tag helpers.
