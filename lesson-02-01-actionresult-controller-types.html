ASP.NET Core MVC Todo Application (.NET 8)

Lesson 2.1: ActionResult, IActionResult, ControllerBase, and Controller

Before we create our Todo model, it helps to understand what MVC actions return and which controller base class fits different application styles. These concepts appear constantly in ASP.NET Core MVC and Web API projects.

Introduction

In ASP.NET Core, controller actions do not usually return raw text directly. Instead, they return result types that describe what the framework should send back to the client. That might be a Razor view, a JSON response, a redirect, or an HTTP status code.

Key Concepts

  • IActionResult is an interface representing an action result.
  • ActionResult is a concrete base class for many MVC results.
  • ASP.NET Core provides helper methods like View(), Json(), Ok(), NotFound(), and RedirectToAction().
  • ControllerBase is commonly used for APIs.
  • ModelState and ModelState.IsValid are available on ControllerBase.
  • A regular Controller without [ApiController] usually checks ModelState.IsValid manually.
  • Controller extends ControllerBase and adds view-related support for MVC apps.

Step-by-Step

What IActionResult Means

using Microsoft.AspNetCore.Mvc;

public sealed class TodoController : Controller
{
    public IActionResult Index()
    {
        return View();
    }
}

IActionResult is a flexible return type. It says, “this action will return something ASP.NET Core can execute as a response,” but it does not lock you into one exact result class.

Returning Different Result Types

public IActionResult Details(int id)
{
    if (id <= 0)
    {
        return BadRequest();
    }

    if (id == 404)
    {
        return NotFound();
    }

    return View();
}

This is one reason IActionResult is useful. A single action can return different response types depending on the situation.

What ActionResult Means

public ActionResult CreateSuccess()
{
    return RedirectToAction(nameof(Index));
}

ActionResult is the base class used by many framework result types. In practice, beginners most often use IActionResult for flexibility, while advanced code may use more specific return types where that improves clarity.

ActionResult<T> for APIs

[HttpGet]
public ActionResult<TodoItem> GetById(int id)
{
    if (id <= 0)
    {
        return BadRequest();
    }

    var item = new TodoItem { Id = id, Title = "Sample todo" };
    return item;
}

ActionResult<T> is common in APIs because it allows you to return either a typed value or an error result like NotFound() or BadRequest().

ControllerBase

using Microsoft.AspNetCore.Mvc;

[ApiController]
[Route("api/[controller]")]
public sealed class TodoApiController : ControllerBase
{
    [HttpGet("{id:int}")]
    public ActionResult<object> Get(int id)
    {
        return Ok(new { Id = id, Title = "API todo" });
    }
}

ControllerBase gives you core web features like model binding, ModelState validation support, and HTTP result helpers, but it does not include Razor view support.

ModelState.IsValid Is Built into ControllerBase

[HttpPost]
public IActionResult Create(TodoItem item)
{
    if (!ModelState.IsValid)
    {
        return BadRequest(ModelState);
    }

    return Ok();
}

You do not need to inherit from Controller just to use ModelState.IsValid. That feature is already available in ControllerBase, which is one reason API controllers can validate input cleanly without Razor view support.

Regular MVC Controllers Usually Validate Manually

public sealed class TodoController : Controller
{
    [HttpPost]
    [ValidateAntiForgeryToken]
    public IActionResult Create(TodoItem item)
    {
        if (!ModelState.IsValid)
        {
            return View(item);
        }

        return RedirectToAction(nameof(Index));
    }
}

In a normal MVC controller, if you are not using [ApiController], ASP.NET Core does not automatically stop the request and return a validation response for you. You usually check ModelState.IsValid yourself and return the same view so the user can fix the form input.

Controller

using Microsoft.AspNetCore.Mvc;

public sealed class TodoController : Controller
{
    public IActionResult Index()
    {
        return View();
    }
}

Controller inherits from ControllerBase and adds MVC view features like View(), PartialView(), ViewData, and TempData. For a Razor-based MVC application like this Todo app, Controller is usually the right choice.

ControllerBase vs Controller

// Best for APIs
public sealed class TodoApiController : ControllerBase
{
}

// Best for MVC with Razor views
public sealed class TodoController : Controller
{
}

Use ControllerBase when your endpoint is focused on data and HTTP responses. Use Controller when your endpoint needs to render views.

Common MVC Result Helpers

return View(model);
return RedirectToAction(nameof(Index));
return NotFound();
return BadRequest();
return Json(new { success = true });
return Content("Hello from MVC");

These helpers create result objects for you. That keeps action methods concise and readable.

Async Version with IActionResult

public async Task<IActionResult> Index(CancellationToken cancellationToken)
{
    await Task.Delay(10, cancellationToken);
    return View();
}

In modern .NET 8 applications, controller actions are often asynchronous, especially when they call databases, APIs, or services.

How This Fits Our Todo App

Our server-rendered Todo MVC application will mainly use Controller because it returns Razor views. Later, when we add AJAX and JSON responses, the same controller can still return IActionResult values like Json(), BadRequest(), or RedirectToAction().

Summary

IActionResult gives controller actions flexibility, ActionResult is the base class behind many result types, ControllerBase is great for APIs, and Controller is usually the correct choice for MVC with Razor views. Understanding these now will make the rest of the Todo app code much easier to follow.
