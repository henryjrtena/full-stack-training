1. Introduction to Domain-Driven Design

What is DDD?

Domain-Driven Design is a software development philosophy that places business logic at the center of your application. Instead of starting with databases and ORM models, DDD starts by deeply understanding the business domain and encoding that understanding directly into code.

CRUD Mindset vs DDD Mindset

Traditional CRUD Approach:

// Entity is just a data container
public class User
{
    public int Id { get; set; }
    public string Email { get; set; }
    public string Name { get; set; }
}

DDD Approach:

// Entity encapsulates business rules
public class User
{
    public UserId Id { get; private set; }
    public Email Email { get; private set; }
    public UserName Name { get; private set; }

    public void ChangeEmail(Email newEmail)
    {
        if (newEmail == null)
            throw new DomainException("Email is required");
        
        Email = newEmail;
    }
}

Why DDD Exists

  • Scattered Business Logic: Rules end up in controllers, services, validators everywhere
  • Difficult to Change: Business rules hidden across layers make refactoring risky
  • Hard to Test: Logic entangled with frameworks is difficult to unit test
  • Lost Intent: Code tells you WHAT it does, not WHY from business perspective
  • Scaling Issues: Simple CRUD becomes unmaintainable as requirements grow

When to Use DDD ✅

  • Complex business domains with rich rules
  • Frequent requirement changes expected
  • Long-term projects (2+ years)
  • Team collaboration with domain experts needed
  • Critical business applications

When NOT to Use DDD ❌

  • Simple CRUD apps (blogs, dashboards, CMS)
  • Prototypes and MVPs
  • Limited business logic
  • Small teams unfamiliar with OOP patterns
  • Real-time dashboards showing data

2. Core DDD Concepts

Entity

Definition: Object with unique identity. Two entities with same data but different IDs are different.

Analogy: People have IDs (SSN). Two people with same name are different due to different IDs.

public class Todo
{
    public TodoId Id { get; private set; }
    public string Title { get; private set; }
    public TodoStatus Status { get; private set; }

    // Equals based on ID, not data
    public override bool Equals(object? obj) =>
        obj is Todo other && Id == other.Id;
}

Value Object

Definition: Object without identity, compared by value, immutable.

Analogy: Money. Two $10 bills are equal; it doesn't matter which one.

public class Email
{
    public string Value { get; }

    public Email(string value)
    {
        if (!IsValidEmail(value))
            throw new DomainException("Invalid email");
        Value = value;
    }

    public override bool Equals(object? obj) =>
        obj is Email e && e.Value == Value;
}

Aggregate & Aggregate Root

Definition: Group of entities/value objects with a root. Root controls access.

Analogy: Car (root) contains engine, wheels, doors. You modify car, car manages parts.

public class TodoList  // Aggregate Root
{
    public TodoListId Id { get; private set; }
    
    private List _todos = new();
    public IReadOnlyList Todos => _todos.AsReadOnly();

    public void AddTodo(string title)
    {
        if (string.IsNullOrWhiteSpace(title))
            throw new DomainException("Title required");
        
        _todos.Add(new Todo(TodoId.Create(), title));
    }

    // Direct access to _todos is prevented
}

Repository

Definition: Abstract data access. Makes aggregates available like a collection.

Analogy: Librarian retrieves books; you don't access the catalog directly.

// Domain layer - interface only
public interface ITodoListRepository
{
    Task GetByIdAsync(TodoListId id);
    Task SaveAsync(TodoList todoList);
}

// Infrastructure layer - implementation
public class TodoListRepository : ITodoListRepository
{
    private readonly AppDbContext _db;
    
    public async Task GetByIdAsync(TodoListId id)
    {
        // EF Core implementation
        var entity = await _db.TodoLists.FirstOrDefaultAsync(x => x.Id == id.Value);
        return entity?.ToDomain();
    }
}

Domain Service

Definition: Stateless service with business logic that spans aggregates.

Analogy: Bank teller handles transfers between accounts (two aggregates).

public class TodoTransferService
{
    private readonly ITodoListRepository _repo;

    public async Task TransferAsync(
        TodoListId from, 
        TodoListId to, 
        TodoId todoId)
    {
        var fromList = await _repo.GetByIdAsync(from);
        var toList = await _repo.GetByIdAsync(to);

        fromList?.RemoveTodo(todoId);
        toList?.AddTodo(todoId);

        await _repo.SaveAsync(fromList!);
        await _repo.SaveAsync(toList!);
    }
}

Application Service

Definition: Orchestrates domain objects. Receives DTOs from controllers, returns DTOs.

Analogy: Restaurant manager. Takes order (DTO), tells kitchen (domain) what to do.

// Application layer
public class CreateTodoUseCase
{
    private readonly ITodoListRepository _repo;

    public async Task ExecuteAsync(CreateTodoRequest request)
    {
        // Load aggregate
        var todoList = await _repo.GetByIdAsync(request.ListId);
        
        // Use domain logic
        todoList.AddTodo(request.Title);
        
        // Save
        await _repo.SaveAsync(todoList);
        
        // Return DTO
        return new TodoDto { Id = todoList.Id, Title = request.Title };
    }
}

Bounded Context

Definition: Explicit boundary where domain language and models are consistent.

Analogy: Hospital has "Cardiology" and "Surgery" departments. "Patient" means different things in each context.

// Billing Bounded Context
public class Invoice  // Entity in Billing context
{
    public InvoiceId Id { get; set; }
    public decimal Amount { get; set; }
}

// Medical Records Bounded Context
public class MedicalRecord  // Entity in Medical context
{
    public RecordId Id { get; set; }
    public string Diagnosis { get; set; }
}

Ubiquitous Language

Definition: Shared vocabulary between developers and domain experts.

Example: Not "CreateTodo" but "AssignTask" if that's the business term.

// Good: reflects business language
namespaceOrderManagement {
    public class Order { ... }
    public class LineItem { ... }
    public void PlaceOrder() { ... }
}

// Bad: generic names hide intent
namespace Generic {
    public class Document { ... }
    public void Process() { ... }
}

5. Base Types: IEntity & IValueObject

Why Base Interfaces?

Creating base interfaces for entities and value objects provides a common contract, makes code more discoverable, and enables generic repository patterns. They enforce DDD principles across your domain model.

IValueObject Interface

// Base interface for all value objects
public interface IValueObject
{
    // Marker interface - enforces immutability through convention
    // Value objects must override Equals and GetHashCode
}

// Base abstract class (optional, but recommended)
public abstract class ValueObject : IValueObject
{
    // Ensure value objects are compared by all properties
    public override bool Equals(object? obj)
    {
        if (obj == null || obj.GetType() != GetType())
            return false;

        var valueObject = (ValueObject)obj;
        return GetAtomicValues().SequenceEqual(valueObject.GetAtomicValues());
    }

    public override int GetHashCode()
    {
        return GetAtomicValues()
            .Select(x => x?.GetHashCode() ?? 0)
            .Aggregate((x, y) => x ^ y);
    }

    // Override in subclass to return properties to compare
    protected abstract IEnumerable GetAtomicValues();

    public static bool operator ==(ValueObject? left, ValueObject? right)
    {
        if (Equals(left, null) ^ Equals(right, null))
            return false;

        return Equals(left, right);
    }

    public static bool operator !=(ValueObject? left, ValueObject? right)
    {
        return !(left == right);
    }
}

IEntity Interface

// Base interface for all entities
public interface IEntity
{
    // Entities have identity, typically defined in subclasses
}

// Generic base class for entities with ID
public abstract class Entity : IEntity where TId : notnull
{
    public TId Id { get; protected set; }

    protected Entity(TId id)
    {
        if (Equals(id, default))
            throw new DomainException("ID cannot be empty");

        Id = id;
    }

    // Entities compared by ID
    public override bool Equals(object? obj)
    {
        if (obj is not Entity entity)
            return false;

        return Equals(entity.Id, Id);
    }

    public override int GetHashCode()
    {
        return Id.GetHashCode();
    }

    public static bool operator ==(Entity? left, Entity? right)
    {
        if (Equals(left, null) ^ Equals(right, null))
            return false;

        return Equals(left, right);
    }

    public static bool operator !=(Entity? left, Entity? right)
    {
        return !(left == right);
    }
}

Usage Example

// Value Object using base class
public class Email : ValueObject
{
    public string Value { get; }

    public Email(string value)
    {
        if (!IsValidEmail(value))
            throw new DomainException("Invalid email");

        Value = value;
    }

    protected override IEnumerable GetAtomicValues()
    {
        yield return Value;
    }

    private static bool IsValidEmail(string email) =>
        email.Contains("@") && email.Length > 5;
}

// Entity using base class
public class Todo : Entity
{
    public string Title { get; private set; }
    public TodoStatus Status { get; private set; }

    public Todo(TodoId id, string title) : base(id)
    {
        if (string.IsNullOrWhiteSpace(title))
            throw new DomainException("Title required");

        Title = title;
        Status = TodoStatus.Pending;
    }

    public void MarkComplete()
    {
        if (Status == TodoStatus.Completed)
            throw new DomainException("Already completed");

        Status = TodoStatus.Completed;
    }
}

Benefits

  • Consistency: All entities/value objects follow same equality rules
  • Less Boilerplate: Inherit equality logic instead of repeating
  • Type Safety: Generic constraints ensure proper ID types
  • Testability: Easy to compare entities and value objects in tests
  • Discoverability: Developers know where to look for domain types

    }

public class UserId : ValueObject
{
    public Guid Value { get; }

    public UserId(Guid value)
    {
        if (value == Guid.Empty)
            throw new DomainException("Invalid user ID");

        Value = value;
    }

    protected override IEnumerable GetAtomicValues()
    {
        yield return Value;
    }
}

// Entity
public class Todo : Entity
{
    public string Title { get; private set; }
    public string? Description { get; private set; }
    public TodoStatus Status { get; private set; }
    public DateTime CreatedAt { get; private set; }

    public Todo(TodoId id, string title) : base(id)
    {
        if (string.IsNullOrWhiteSpace(title))
            throw new DomainException("Title required");

        Title = title;
        Status = TodoStatus.Pending;
        CreatedAt = DateTime.UtcNow;
    }

    public void UpdateTitle(string newTitle)
    {
        if (string.IsNullOrWhiteSpace(newTitle))
            throw new DomainException("Title cannot be empty");

        Title = newTitle;
    }

    public void MarkComplete()
    {
        if (Status == TodoStatus.Completed)
            throw new DomainException("Already completed");

        Status = TodoStatus.Completed;
    }
}

// Aggregate Root
public class TodoList : Entity
{
    public UserId OwnerId { get; private set; }
    public string Name { get; private set; }

    private List _todos = new();
    public IReadOnlyList Todos => _todos.AsReadOnly();

    public TodoList(TodoListId id, UserId ownerId, string name) 
        : base(id)
    {
        if (string.IsNullOrWhiteSpace(name))
            throw new DomainException("Name required");

        OwnerId = ownerId;
        Name = name;
    }

    public void AddTodo(string title)
    {
        if (string.IsNullOrWhiteSpace(title))
            throw new DomainException("Title required");

        var todo = new Todo(TodoId.Create(), title);
        _todos.Add(todo);
    }

    public void CompleteTodo(TodoId todoId)
    {
        var todo = _todos.FirstOrDefault(t => t.Id == todoId);
        if (todo == null)
            throw new DomainException("Todo not found");

        todo.MarkComplete();
    }

    public void RemoveTodo(TodoId todoId)
    {
        var todo = _todos.FirstOrDefault(t => t.Id == todoId);
        if (todo == null)
            throw new DomainException("Todo not found");

        _todos.Remove(todo);
    }
}

public class CreateTodoRequest

// UseCase
public class CreateTodoUseCase
{
    private readonly ITodoListRepository _repository;

    public CreateTodoUseCase(ITodoListRepository repository)
    {
        _repository = repository;
    }

    public async Task ExecuteAsync(CreateTodoRequest request)
    {
        // Load aggregate
        var todoList = await _repository.GetByIdAsync(
            new TodoListId(request.ListId));
        
        if (todoList == null)
            throw new ApplicationException("TodoList not found");

        // Use domain logic
        todoList.AddTodo(request.Title);

        // Save
        await _repository.SaveAsync(todoList);

        //Return DTO
        var newTodo = todoList.Todos.Last();
        return new TodoDto 
        { 
            Id = newTodo.Id.Value,
            Title = newTodo.Title,
            Status = newTodo.Status.ToString()
        };
    }
}

3️⃣ Infrastructure Layer (TodoApp.Infrastructure)

// EF Core DbContext
public class AppDbContext : DbContext
{
    public DbSet TodoLists { get; set; }

    protected override void OnModelCreating(ModelBuilder builder)
    {
        builder.Entity().HasKey(x => x.Id);
        builder.Entity()
            .Property(x => x.Id)
            .HasConversion(x => x.Value, x => new TodoListId(x));
    }
}

// Repository Implementation
public class TodoListRepository : ITodoListRepository
{
    private readonly AppDbContext _db;

    public TodoListRepository(AppDbContext db)
    {
        _db = db;
    }

    public async Task GetByIdAsync(TodoListId id)
    {
        return await _db.TodoLists
            .FirstOrDefaultAsync(x => x.Id == id);
    }

    public async Task SaveAsync(TodoList todoList)
    {
        _db.TodoLists.Update(todoList);
        await _db.SaveChangesAsync();
    }
}

Extension Method Pattern

// Infrastructure/DependencyInjection.cs
public static class InfrastructureExtensions
{
    public static IServiceCollection AddInfrastructure(
        this IServiceCollection services,
        IConfiguration config)
    {
        services.AddDbContext(
            opts => opts.UseSqlServer(
                config.GetConnectionString("DefaultConnection")));

        services.AddScoped();

        return services;
    }
}

// Application/DependencyInjection.cs
public static class ApplicationExtensions
{
    public static IServiceCollection AddApplication(
        this IServiceCollection services)
    {
        services.AddScoped();
        services.AddScoped();
        services.AddScoped();

        return services;
    }
}

8. Best Practices

✅ Keep Domain Pure

// Good: no external dependencies
public class Email
{
    public string Value { get; }
    
    public Email(string value)
    {
        if (!value.Contains("@"))
            throw new DomainException("Invalid email");
        Value = value;
    }
}

// Bad: depends on external service
public class EmailWithValidation
{
    public string Value { get; }
    
    public EmailWithValidation(string value, IEmailValidator validator)
    {
        // Creates dependency on infrastructure
    }
}

✅ Avoid Anemic Models

// Bad: data container with no logic
public class Todo
{
    public int Id { get; set; }
    public string Title { get; set; }
    public bool IsCompleted { get; set; }
}

// Good: encapsulates behavior
public class Todo
{
    public TodoId Id { get; private set; }
    public string Title { get; private set; }
    public TodoStatus Status { get; private set; }

    public void Complete()
    {
        if (Status == TodoStatus.Completed)
            throw new DomainException("Already completed");
        Status = TodoStatus.Completed;
    }
}

✅ Use Value Objects

// Good: strongly typed
public void UpdateEmail(Email newEmail) { }

// Bad: primitive obsession
public void UpdateEmail(string newEmail) { }

✅ Respect Aggregate Boundaries

// Good: access through root only
var todoList = await repository.GetByIdAsync(id);
todoList.AddTodo("New task");  // Through aggregate root

// Bad: direct access
var todos = await dbContext.Todos
    .Where(t => t.ListId == id)
    .ToListAsync();

9. Common Mistakes

❌ Putting EF Core in Domain

// WRONG: Domain depends on infrastructure
public class Todo
{
    [DatabaseGenerated(DatabaseGeneratedOption.Identity)]
    public int Id { get; set; }
    
    [Required]
    [MaxLength(100)]
    public string Title { get; set; }
}
// RIGHT: Domain is pure
public class Todo
{
    public TodoId Id { get; private set; }
    public string Title { get; private set; }
}

❌ Using DTOs in Domain

// WRONG
public class Order
{
    public OrderDto ToDto() { }
}
// RIGHT: DTO conversion in application/infrastructure
public class OrderMappings
{
    public static OrderDto ToDto(Order order) { }
}

❌ Fat Controllers

// WRONG: business logic in controller
[HttpPost]
public async Task Create(CreateOrderRequest req)
{
    if (req.Amount < 0)  // Business rule
        return BadRequest("Amount must be positive");
    
    var order = new Order(req.CustomerId, req.Amount);
    await _db.SaveChangesAsync();
    return Ok();
}
// RIGHT: use cases handle logic
[HttpPost]
public async Task Create(CreateOrderRequest req)
{
    var result = await _createOrderUseCase.ExecuteAsync(req);
    return Ok(result);
}

❌ Treating DDD as Just Folders

DDD is NOT about creating Domain/Application/Infrastructure folders. It's about encapsulating business logic, protecting aggregates, and using value objects. Folder structure only reflects understanding.

❌ Ignoring Bounded Contexts

Creating one giant domain model instead of separate bounded contexts for different business areas. Example: Order context should be separate from Shipping context.

Summary

Domain-Driven Design places business logic at the heart of your application. By using entities, value objects, aggregates, and repositories, you create code that's testable, maintainable, and reflects your business reality. Start with clear domain boundaries, protect your aggregates, and keep infrastructure concerns separate. The initial investment in DDD pays off as your application grows.
