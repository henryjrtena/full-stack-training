Git Fundamentals

Master Git workflows, branching strategies, merge conflict resolution, and professional development practices. Learn branch naming conventions and habits that prevent conflicts and streamline pull requests.

Introduction to Git

Git is a distributed version control system that tracks changes to your code. Understanding branches, merging, and conflict resolution is essential for collaborative development. This lesson covers practical workflows and best practices for team environments.

  • Git stores a complete history of every change in your repository.
  • Branches allow parallel development without affecting the main codebase.
  • Merges combine changes from different branches.
  • Conflicts occur when changes overlap; they must be resolved manually.
  • Professional workflows use naming conventions and regular syncing to prevent conflicts.

Creating and Managing Branches

Creating a New Branch

# Create a new branch locally (but don't switch to it)
git branch feature/user-authentication

# Create and switch to a new branch in one command
git checkout -b feature/user-authentication

# Modern equivalent using git switch (Git 2.23+)
git switch -c feature/user-authentication

# List all local branches
git branch

# List all branches (local and remote)
git branch -a

# List remote branches only
git branch -r

The -b flag means "create and switch" to the new branch. Always create branches from a clean working directory to avoid carrying uncommitted changes into the new branch.

Understanding Branch Pointers

# Your current branch pointer and recent commits
git log --oneline --graph --all

# Example output:
# * 3a2b1c0 (HEAD -> feature/user-authentication) Add login form
# | * 2f1e9d8 (main) Bump version to 1.2.0
# |/
# * 1a0b9c7 Refactor database module
# * 0f9e8d6 Initial commit

HEAD points to your current branch. A branch is just a pointer to a specific commit. When you create a new branch, you're creating a new pointer that references the current commit.

Switching Between Branches

# Switch to an existing branch using checkout
git checkout main

# Modern equivalent using switch
git switch main

# Switch to a branch and pull latest changes
git switch main && git pull

# Switch back to the previous branch
git checkout -

# List branches and switch interactively
git branch -a

Before switching branches, ensure your working directory is clean. Commit or stash uncommitted changes to avoid losing work.

Fetching, Pulling, and Staying in Sync

Fetch vs Pull

# Fetch: Download remote changes WITHOUT merging
git fetch origin

# Fetch all remotes
git fetch --all

# After fetching, see what changed on remote
git log ..origin/main

# Pull: Fetch + Merge in one command
git pull origin main

# Pull with rebase (preferred for cleaner history)
git pull --rebase origin main

# Pull from current branch (if tracking is set up)
git pull

Fetch is safe—it only downloads changes without modifying your local branches. Pull automatically merges, which can introduce merge commits. Use fetch to review changes before merging.

Nice to Have Habit: Frequent Fetching Minimizes Conflicts

Best Practice: Fetch from the parent branch (usually main/dev) frequently, even while developing on your feature branch. This prevents your branch from drifting too far from the team's changes, reducing merge conflicts during pull requests. 
# While on your feature branch, frequently sync with main
# Step 1: Fetch the latest from remotes
git fetch origin

# Step 2: Check how far your branch is from main
git log --oneline main..HEAD  # Commits unique to your branch
git log --oneline HEAD..main  # Commits from main you don't have

# Step 3: Merge (or rebase) main into your feature branch
# Option A: Merge (creates a merge commit)
git merge origin/main

# Option B: Rebase (replays your commits on top of main)
git rebase origin/main

# Step 4: Continue developing with less conflict risk later

Rebasing is often preferred because it keeps the history linear and cleaner. However, use caution: never rebase branches that others are working on, as it rewrites history.

Workflow: Regular Syncing Strategy

# Daily workflow to minimize conflicts
# Step 1: Start your day or begin a coding session
git fetch origin

# Step 2: Check if main ha d updates
git log --oneline --graph main..origin/main

# Step 3: If main has new commits, sync your branch
git rebase origin/main
# or
git merge origin/main

# Step 4: Continue coding
# ... make your changes, commit ...

# Step 5: Before pushing, sync one last time
git fetch origin
git rebase origin/main  # or git merge origin/main

# Step 6: Push your feature branch
git push origin feature/user-authentication

This habit of frequent fetching and syncing prevents your branch from accumulating months of diverged work, which would result in massive merge conflicts.

Understanding Merge Conflicts

What Causes Merge Conflicts?

# Scenario: You and a teammate edit the same file at the same location
# Your branch: feature/login - modifies src/auth.cs line 10-15
# Main branch: also modifies src/auth.cs line 10-15

# When you try to merge, Git doesn't know which version to keep
git merge origin/main
# CONFLICT (content): Merge conflict in src/auth.cs
# CONFLICT (content): Merge conflict in src/models/User.cs
# Automatic merge failed; fix conflicts and then commit the result.

Conflicts happen when two branches modify the same lines of code differently. Git cannot automatically decide which change is correct.

Conflict Markers and Resolution

// src/auth.cs - shows conflict markers
<<<<<<< HEAD
    public string Login(string username, string password)
    {
        // Your implementation
        return ValidateUser(username, password);
    }
=======
    public async Task<string> LoginAsync(string username, string password)
    {
        // Their implementation
        return await AuthenticationService.ValidateAsync(username, password);
    }
>>>>>>> origin/main

The section between <<<<<<< and ======= is your version. The section between ======= and >>>>>>> is the incoming version.

Resolving Conflicts Manually

// Step 1: Open the conflicted file and decide what to keep
// Resolved version - combining the best of both approaches:
public async Task<string> LoginAsync(string username, string password)
{
    // Use the async version with proper validation
    if (string.IsNullOrEmpty(username) || string.IsNullOrEmpty(password))
        return null;
    
    return await AuthenticationService.ValidateAsync(username, password);
}

// Step 2: Remove the conflict markers (all <<<, ===, >>> lines)

// Step 3: Check status
git status

// Step 4: Stage the resolved file
git add src/auth.cs

// Step 5: Commit the merge
git commit -m "Merge main: resolve auth.cs conflict"

// Step 6: continue with your work or push
git push origin feature/user-authentication

Using Tools for Conflict Resolution

# Use Visual Studio Code as the merge tool
git config --global core.editor "code"

# Configure a visual merge tool (e.g., Beyond Compare, KDiff3)
git config --global merge.tool vscode
git config --global mergetool.vscode.cmd "code --wait"

# When a conflict occurs, launch the merge tool
git mergetool

# Abort a merge if it becomes too complicated
git merge --abort

# Or abort a pull
git pull --abort

Most IDEs like Visual Studio Code have built-in Git conflict resolution interfaces with visual comparisons, making it easier to choose the right version.

Branch Naming Conventions

Standard Branch Types

# Development branch - where features merge before release
git checkout -b develop
git push origin develop

# Feature branch - new functionality
git checkout -b feature/user-authentication
git checkout -b feature/payment-integration
git checkout -b feature/export-to-csv

# Bugfix branch - fixing bugs in development
git checkout -b bugfix/login-validation-error
git checkout -b bugfix/null-reference-exception

# Hotfix branch - urgent fixes for production
git checkout -b hotfix/security-patch
git checkout -b hotfix/critical-data-loss

# Version/Release branch - preparing a release
git checkout -b release/v1.2.0
git checkout -b release/2024-q1

Naming Best Practices

  • Use lowercase: Branch names are case-sensitive; lowercase prevents confusion.
  • Use hyphens, not underscores: feature/user-auth not feature_user_auth.
  • Be descriptive: feature/two-factor-auth is better than feature/auth.
  • Include ticket numbers if applicable: feature/JIRA-123-user-profile.
  • Keep names concise: Avoid excessively long branch names.
  • Avoid special characters: Stick to alphanumerics, hyphens, and slashes.

Complete Branching Strategy Example

# Main branch (production-ready)
main
  ↑
  │ (PR: release/v1.2.0 → main)
  │
develop (staging/integration)
  ├─ feature/user-authentication
  │   └─ (regular sync: git rebase origin/develop)
  │
  ├─ feature/payment-integration
  │   └─ (regular sync: git rebase origin/develop)
  │
  ├─ bugfix/login-validation
  │   └─ (regular sync: git rebase origin/develop)
  │
  └─ release/v1.2.0
      ↑
      │ (after testing, this merges to main with tag v1.2.0)
      │ (and back-merges to develop)

hotfix/security-patch
  ↑
  │ (created from main for critical production fixes)
  │ (merges back to main AND develop)

Complete Git Workflow Example

Scenario: Developing a Feature with Conflict Management

# Day 1: Start a new feature
git checkout -b feature/user-dashboard
git push -u origin feature/user-dashboard

# Day 2: After a few commits, sync with the team's latest work
git fetch origin
git rebase origin/develop  # or merge if you prefer
# Fix any conflicts that arise

# Day 3: Continue development, commit regularly
git add src/Dashboard.cs
git commit -m "Add dashboard layout and styling"

# Day 4: Before finishing, sync one more time
git fetch origin
git rebase origin/develop  # Minimize conflicts in PR later

# Day 5: Push the feature branch
git push origin feature/user-dashboard

# Create a Pull Request (PR) on GitHub/GitLab/Azure DevOps
# Describe what the feature does and link any related issues

# Peer review: Address feedback
git add src/Dashboard.cs
git commit -m "Address review feedback: improve accessibility"
git push origin feature/user-dashboard  # PR updates automatically

# After approval, merge the PR
# Option A: Squash commits (cleaner history)
# Option B: Create a merge commit (preserves feature history)
# Option C: Rebase and fast-forward (linear history)

# After merge, clean up
git checkout develop
git pull origin develop
git branch -d feature/user-dashboard  # Delete local branch
git push origin --delete feature/user-dashboard  # Delete remote branch

Handling a Merge Conflict During This Workflow

# Day 4: When syncing, a conflict occurs
git fetch origin
git rebase origin/develop
# CONFLICT (content): Merge conflict in src/Services/UserService.cs

# Step 1: Check what files have conflicts
git status

# Step 2: Open the conflicted file and resolve
# (Edit the file, remove conflict markers, keep the correct logic)

# Step 3: Mark as resolved
git add src/Services/UserService.cs

# Step 4: Continue the rebase
git rebase --continue

# Step 5: If something goes wrong, abort and try --merge instead
git rebase --abort
git merge origin/develop
# Resolve conflicts the same way

# Step 6: Push with force (only because you rebased)
git push origin feature/user-dashboard --force-with-lease

Use --force-with-lease instead of --force because it's safer—it won't overwrite remote changes made by teammates.

Summary of Best Practices

  • Fetch regularly: git fetch origin daily to stay aware of team changes.
  • Sync your branch frequently: Merge or rebase the parent branch into your feature branch often.
  • Commit frequently: Small, logical commits are easier to review and less prone to conflicts.
  • Use descriptive branch names: Follow conventions like feature/feature-name, bugfix/bug-name, hotfix/issue-name.
  • Keep feature branches short-lived: Aim to merge within a few days, not weeks or months.
  • Resolve conflicts carefully: Take time to understand both versions before merging.
  • Push with --force-with-lease: Safer than --force when dealing with rebased commits.
  • Delete stale branches: Keep the repository clean after merging.
  • Review PRs thoroughly: Prevent conflicts by catching integration issues early.
  • Communicate with your team: If modifying the same files, coordinate or pair program to reduce conflicts.

Key Takeaways

Git branching is fundamental to collaborative development. By adopting consistent naming conventions, syncing frequently, and resolving conflicts methodically, you'll prevent the common nightmare of massive, complicated merge conflicts. The habit of fetching from the parent branch regularly is perhaps the single most important practice for reducing merge pain.
