Performance & UI Optimization

Lesson 16: Lazy Loading & Debouncer

This lesson covers two critical optimization techniques: lazy loading in Entity Framework Core and debouncer patterns for handling rapid user input. Learn how to balance database efficiency with responsive user interfaces.

Introduction

Entity Framework Core can load related data in different ways. One of those ways is lazy loading, where related data is loaded only when you first access it. This can make coding feel convenient, but it also has tradeoffs that developers need to understand clearly.

Key Concepts

  • Lazy loading retrieves related data only when it is accessed.
  • Eager loading uses Include to load related data immediately.
  • IEnumerable works with in-memory sequences.
  • IQueryable lets EF Core build SQL queries before execution.
  • Lazy loading can be convenient, but it can also create extra database queries.

Step-by-Step

Install the Lazy Loading Package

dotnet add package Microsoft.EntityFrameworkCore.Proxies

EF Core lazy loading with proxies requires the proxies package in addition to the main EF Core packages already introduced in the previous lesson.

Example Models with Navigation Properties

namespace TodoMvcApp.Models;

public sealed class TodoItem
{
    public int Id { get; set; }
    public string Title { get; set; } = string.Empty;
    public int CategoryId { get; set; }

    public virtual TodoCategory? Category { get; set; }
}

public sealed class TodoCategory
{
    public int Id { get; set; }
    public string Name { get; set; } = string.Empty;

    public virtual ICollection<TodoItem> TodoItems { get; set; } = [];
}

The virtual keyword is important here because the lazy loading proxy needs to override navigation properties so it can load related entities on demand.

Configure Lazy Loading in Program.cs

builder.Services.AddDbContext<TodoDbContext>(options =>
    options.UseLazyLoadingProxies()
           .UseSqlServer(builder.Configuration.GetConnectionString("TodoDb")));

This enables lazy loading proxies for your EF Core context. Once configured, related navigation properties can load automatically when first used.

DbContext Example

using Microsoft.EntityFrameworkCore;
using TodoMvcApp.Models;

namespace TodoMvcApp.Data;

public sealed class TodoDbContext(DbContextOptions<TodoDbContext> options)
    : DbContext(options)

    public DbSet<TodoItem> TodoItems => Set<TodoItem>();
    public DbSet<TodoCategory> TodoCategories => Set<TodoCategory>();
}

Controller Example

using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;
using TodoMvcApp.Data;

namespace TodoMvcApp.Controllers;

public sealed class TodoController(TodoDbContext dbContext) : Controller
{
    public async Task<IActionResult> Index(CancellationToken cancellationToken)
    {
        var items = await dbContext.TodoItems
            .OrderBy(x => x.Title)
            .ToListAsync(cancellationToken);

        return View(items);
    }
}

Notice that this query does not call Include(x => x.Category). If lazy loading is enabled, the related category can still load later when the Razor view touches item.Category.

When the view accesses item.Category?.Name, EF Core may trigger a separate query for each item if the category was not already loaded. This is convenient, but it can also create the classic N+1 query problem.

IEnumerable vs IQueryable

IQueryable<TodoItem> query = dbContext.TodoItems;

query = query.Where(x => x.Title.Contains("MVC"));

IEnumerable<TodoItem> items = await query.ToListAsync(cancellationToken);

IQueryable represents a query that EF Core can translate into SQL. The query is not executed immediately. IEnumerable represents an in-memory sequence that you can loop through after the data has already been loaded.

Why IQueryable Matters

// Database-side filtering
var query = dbContext.TodoItems.Where(x => x.Priority >= 3);

// Query executes here
var items = await query.ToListAsync(cancellationToken);

As long as the data is still IQueryable, EF Core can build the SQL query efficiently. Once the data becomes IEnumerable, later operations happen in memory instead of in SQL.

Lazy Loading vs Include

// Lazy loading approach
var items = await dbContext.TodoItems.ToListAsync(cancellationToken);

// Eager loading approach
var itemsWithCategory = await dbContext.TodoItems
    .Include(x => x.Category)
    .ToListAsync(cancellationToken);

Include is often safer when you already know the view will need related data. Lazy loading can make code simpler, but eager loading gives you more predictable SQL behavior.

When to Use Lazy Loading Carefully

  • It is useful for demos, prototypes, and simple navigation scenarios.
  • It can hide extra queries and hurt performance in loops.
  • It is often better to use Include when a view definitely needs related data.
  • Always think about what SQL your code may generate, especially inside Razor loops.

Debouncer Pattern for Responsive UIs

What is Debouncing?

Debouncing is a technique that prevents a function from being called too frequently by delaying its execution and resetting the timer each time it is triggered. It is commonly used for search inputs, autocomplete fields, and form validation to reduce unnecessary server calls.

Client-Side Debouncer (JavaScript)

function debounce(func, delay) {
    let timeoutId;
    return function (...args) {
        clearTimeout(timeoutId);
        timeoutId = setTimeout(() => func(...args), delay);
    };
}

const handleSearch = debounce((query) => {
    console.log("Searching for:", query);
    // Make API call here
    fetch(`/api/search?q=${query}`)
        .then(response => response.json())
        .then(data => console.log(data));
}, 500);

document.getElementById('searchInput').addEventListener('input', (e) => {
    handleSearch(e.target.value);
});

This example delays the search request by 500ms. If the user types again before 500ms has passed, the timer resets, preventing multiple rapid requests.

HTML Example with Real-Time Search

<input

    id="searchInput" 
    placeholder="Search todos..."
    autocomplete="off"
/>

<ul id="results" style="display: none;">
    <!-- Search results will appear here -->

<script>
const searchInput = document.getElementById('searchInput');
const resultsContainer = document.getElementById('results');

function debounce(func, delay) {
    let timeoutId;
    return function (...args) {
        clearTimeout(timeoutId);
        timeoutId = setTimeout(() => func(...args), delay);
    };
}

const performSearch = debounce(async (query) => {
    if (!query.trim()) {
        resultsContainer.style.display = 'none';
        return;
    }

    try {
        const response = await fetch(`/api/todos/search?q=${encodeURIComponent(query)}`);
        const data = await response.json();

        resultsContainer.innerHTML = '';
        data.forEach(item => {
            const li = document.createElement('li');
            li.textContent = item.title;
            resultsContainer.appendChild(li);
        });
        resultsContainer.style.display = 'block';
    } catch (error) {
        console.error('Search failed:', error);
    }
}, 300);

searchInput.addEventListener('input', (e) => {
    performSearch(e.target.value);
});
</script>

Server-Side Search Endpoint (ASP.NET Core Controller)

[ApiController]
[Route("api/[controller]")]
public class TodosController : ControllerBase
{
    private readonly TodoDbContext _dbContext;

    public TodosController(TodoDbContext dbContext)
    {
        _dbContext = dbContext;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(string q, CancellationToken cancellationToken)
    {
        if (string.IsNullOrWhiteSpace(q))
            return Ok(Array.Empty<object>());

        var results = await _dbContext.TodoItems
            .Where(t => t.Title.Contains(q))
            .Take(10)
            .Select(t => new { t.Id, t.Title })
            .ToListAsync(cancellationToken);

        return Ok(results);
    }
}

The server endpoint handles the actual search query. Debouncing on the client ensures the server is not called repeatedly while the user is still typing.

Debouncer with Loading Indicator

    type="text" 
    id="searchInput" 
    placeholder="Search todos..."
/>
<div id="loading" style="display: none;">Searching...</div>
<ul id="results"></ul>

<script>
function debounce(func, delay) {
    let timeoutId;
    return function (...args) {
        clearTimeout(timeoutId);
        timeoutId = setTimeout(() => func(...args), delay);
    };
}

const performSearch = debounce(async (query) => {
    const loading = document.getElementById('loading');
    const results = document.getElementById('results');
    
    if (!query.trim()) {
        results.innerHTML = '';
        loading.style.display = 'none';
        return;
    }

    loading.style.display = 'block';
    
    try {
        const response = await fetch(`/api/todos/search?q=${encodeURIComponent(query)}`);
        const data = await response.json();

        results.innerHTML = '';
        if (data.length === 0) {
            results.innerHTML = '<li>No results found</li>';
        } else {
            data.forEach(item => {
                const li = document.createElement('li');
                li.textContent = item.title;
                results.appendChild(li);
            });
        }
    } catch (error) {
        results.innerHTML = '<li>Error searching</li>';
        console.error('Search failed:', error);
    } finally {
        loading.style.display = 'none';
    }
}, 400);

document.getElementById('searchInput').addEventListener('input', (e) => {
    performSearch(e.target.value);
});
</script>

When to Use Debouncing

  • Search inputs that trigger API calls on each keystroke.
  • Real-time validation fields (username availability, email verification).
  • Auto-save features to prevent excessive database writes.
  • Window resize handlers or scroll event listeners.
  • Form input fields with expensive computations.

Debouncing vs Throttling

// Debounce: Wait until user stops typing (good for search)
function debounce(func, delay) {
    let timeoutId;
    return function (...args) {
        clearTimeout(timeoutId);
        timeoutId = setTimeout(() => func(...args), delay);
    };
}

// Throttle: Execute at most once every X milliseconds (good for scroll)
function throttle(func, delay) {
    let lastCall = 0;
    return function (...args) {
        const now = Date.now();
        if (now - lastCall >= delay) {
            func(...args);
            lastCall = now;
        }
    };
}

Debounce: Resets when re-triggered; executes only after a pause. Best for searches and autocomplete. Throttle: Executes at regular intervals regardless of re-triggers. Best for scroll events and animations.

Summary

This lesson covered two essential optimization techniques: Lazy Loading for database efficiency and Debouncer for responsive user interfaces. Lazy loading can make EF Core code feel natural, but it comes with performance tradeoffs. Debouncing prevents excessive API calls and improves perceived performance. Together, these patterns help you build applications that are both efficient and responsive.
